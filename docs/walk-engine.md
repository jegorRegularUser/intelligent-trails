# Дизайн: движок прогулок `src/lib/walk`

> Реализация ТЗ из `docs/PRODUCT.md` (раздел «Метрика хорошей прогулки» — гейты).
> Границы: чистый детерминированный движок. Ни UI, ни сети, ни хранения —
> движок получает готовых кандидатов и порт маршрутизации, выдаёт план.

## 1. Роль и границы

```
UI / server actions ──(GeoPlace[])──┐
                                    ▼
                         createWalkPlan(input, ports)
                                    │  ports: matrix(sources, targets), route(waypoints)
                                    ▼
                         WalkPlanResult (3 альтернативы | честный отказ)
```

Движок **не знает**, откуда кандидаты (Overpass, Mongo-дамп) и кто роутит
(OSRM, OpenRouteService, фейк). Он только комбинирует факты.

## 2. Контракт данных и порты

Локальные структурные типы в `src/lib/walk/types.ts` — **без импорта
`lib/geo/types`** (кроме документации). TS-структурность делает их взаимно
совместимыми: `GeoPlace[]` передаётся как `WalkPlace[]` без адаптера, а любой
`GeoProvider` удовлетворяет `WalkRoutingPort`.

| Локальный тип | Структурный двойник в geo/types | Отличия |
|---|---|---|
| `WalkLatLng = [number, number]` | `LatLng` | нет — порядок `[lat, lng]`, единицы: метры и секунды (правило 5 ADR-001) |
| `WalkPlace` | `GeoPlace` | только поля, нужные движку (`id, name, category, coordinates, rating?`); лишние поля источника просто игнорируются |
| `WalkMatrixCell` | `MatrixCell` | `null`-ячейки = недостижимо пешком — контракт обязателен |
| `WalkRouteSegment` | `RouteSegment` | `source` — необязательная строка |
| `WalkRoutingPort` | `GeoProvider` (срез) | только `matrix` + `route`; чанкинг ≤40 точек — забота порта, не движка |

```ts
interface WalkRoutingPort {
  /** Маршрут по реальным улицам. Бросает при недостижимости. */
  route(req: { waypoints: WalkLatLng[] }): Promise<WalkRouteSegment>;
  /** Плоская матрица ячеек; null = недостижимо. */
  matrix(sources: WalkLatLng[], targets: WalkLatLng[]): Promise<WalkMatrixCell[]>;
}
```

Почему `route` принимает `{ waypoints }`, а не сам массив: так `GeoProvider`
совместим с портом по строгой контравариантности аргумента (`RouteRequest`
допускает лишнее опциональное поле `alternatives`), и адаптер не нужен.

## 3. Вход / выход

```ts
interface WalkInput {
  start: WalkLatLng;
  end?: WalkLatLng;        // обязателен при isLoop = false (режим А→Б)
  budgetMinutes: number;   // > 0; первое ограничение генератора
  categoryWeights: Record<string, number>; // вес категории; отсутствие/<=0 = категория не нужна
  candidates: WalkPlace[];
  isLoop: boolean;
  walkingSpeedKmh?: number;               // default 4.5
  categoryStayMinutes?: Record<string, number>; // переопределение таблицы stay
}

type WalkPlanResult =
  | { ok: true; plans: WalkPlan[] }              // до 3, отсортированы
  | { ok: false; failure: WalkFailure };
```

Расширение относительно ТЗ: добавлено поле `end?` — режим «А→Б, но красиво» по
PRODUCT.md невозможен без финиша, а коридор считается именно до него. `isLoop =
false` без `end` → `INVALID_INPUT`.

## 4. Алгоритм по шагам

1. **Валидация** (`INVALID_INPUT`): координаты конечны, `budgetMinutes > 0`,
   `speed ∈ (0, 15]`, `categoryWeights` непуст, `end` присутствует при
   `isLoop = false`.
2. **Зона поиска** (см. §5): коридор к финишу (А→Б) или радиус (петля).
3. **Отбор кандидатов**: фильтр по зоне + вес категории > 0 → скор → **cap 60**.
4. **Матрица**: один вызов `matrix(все_точки, все_точки)` — старт, финиш
   (А→Б) и шорт-лист. Кандидаты с `null`-ячейкой к старту (и к финишу в А→Б)
   выбрасываются — честная деградация. Между якорями `null` = ребро бесконечной
   стоимости: NN/2-opt его обходят; если избежать не удалось — вариант плана
   отбрасывается.
5. **Отказы на дешёвых проверках** до всякой сборки:
   - без порта, нижние оценки: любой пеший путь ≥ прямой линии, поэтому
     А→Б `прямая/скорость > 1.1×бюджета` → `NOT_ENOUGH_TIME`; петля —
     `min(2·прямая/скорость + stay)` по кандидатам > 1.1×бюджета →
     `NOT_ENOUGH_TIME`;
   - по матрице: А→Б — прямая ячейка старт→финиш `null` → `NO_ROUTE`,
     время > 1.1×бюджета → `NOT_ENOUGH_TIME`; петля —
     `min(2·t(старт,c) + stay(c))` по живым кандидатам > 1.1×бюджета →
     `NOT_ENOUGH_TIME`; живых кандидатов < 2 → `NO_CANDIDATES`
     (2 якоря — минимум продуктовой метрики, мусорный план из одного якоря не
     отдаём; в А→Б чистый маршрут без якорей полезен сам по себе — план
     возвращается с честно упавшим гейтом `anchors`).
6. **Подбор количества остановок** (жадный): ранжированный шорт-лист
   просматривается по порядку; кандидат добавляется, если план с ним
   ≤ 1.1×бюджета (порядок пересчитывается, стоимость — по матрице), иначе
   пропускается (дорогой кандидат не блокирует дешёвых следующих). Верхняя
   граница — `MAX_STOPS = 6` (PRODUCT: 2–4 остановки, +запас для длинных
   бюджетов; гейт `anchors` требует ≥ 2).
7. **Порядок обхода**: NN по матрице минут + 2-opt (§7).
8. **Реальные ноги**: для финального порядка — `route()` на каждую ногу.
   Геометрия и время ног — от роутинга (PRODUCT: «улицы, а не прямые линии»).
   Упавший `route()` → вариант плана отбрасывается. Планирование считается по
   матрице, финальный бюджет — по метрикам реальных ног (согласованы в рамках
   одного провайдера).
9. **Гейты** (§8) → `gateReport`. **Причины якорей** (§9). **Скор** (§10).
10. **Альтернативы**: шаги 2–9 повторяются на 3 вариантах параметров (§11),
    результаты сортируются: все гейты pass → выше скор → короче.

### Сложность

| Шаг | Стоимость | Практика |
|---|---|---|
| Отбор + скор | O(n) | n — входные кандидаты |
| Матрица | O(m²) ячеек, m ≤ 62 | чанкинг ≤40 — на стороне порта; ~4 запроса ORS |
| Жадный подбор | O(m · k²) | k ≤ 6: NN+2-opt на каждой примерке ≈ 60·36 = 2 160 оп. |
| 2-opt | O(k²) на проход, ≤ k проходов | микро |
| Гейт «та же улица» | O(L² · s²), L ≤ 7 ног, s ≤ 64 точки | ≈ 200 тыс. дешёвых оп. |

Всё — миллисекунды на клиентских мощностях; сеть (матрица+ноги) доминирует.

## 5. Зона поиска

**А→Б — коридор.** Ширина от прямой `start→end`:
`W = clamp(0.3 · d, 300 м, 1500 м)`. Отбор: расстояние точка→отрезок ≤ W.
Почему отрезок, а не конус направления: конус из `placeRanking.ts` считает
dot product по сырым градусам — 1° широты ≠ 1° долготы в метрах, конус
перекошен вдоль параллели, и у цели сбоку он вообще вырождается. Расстояние до
осевой линии — та же идея без искажения и без произвольного угла раствора.

**Петля — радиус.** `R = v·(0.6·budget)/4`:
`0.6·budget` — ходячая доля бюджета (40% резервируем под stay и кривизну улиц),
делитель 4 соответствует кольцу через якорь на противоположной стороне
(длина кольца ≈ 4·R для ромбовидной формы). Пример: 60 мин → 36 мин ходьбы →
2.7 км пешком → R ≈ 0.7 км. Радиус — эвристика зоны, не граница маршрута:
реальные ноги всё равно считает роутинг, а бюджет проверяется после.

Проекция для метров: локальная равнопромежуточная (`equirectangular`) вокруг
центра зоны — на масштабе города (<10 км) ошибка << 1%.

## 6. Время стоянок (stay)

Бюджет = Σ ходьба + Σ stay. Stay берётся из таблицы по категории
(переопределяется `categoryStayMinutes`):

| категория | park | museum | cafe | restaurant | bar | viewpoint | attraction | cinema | shopping | прочее |
|---|---|---|---|---|---|---|---|---|---|---|
| минут | 25 | 45 | 20 | 40 | 30 | 15 | 25 | 90 | 40 | 20 |

Числа — продуктовые согласующие PRODUCT («1–2 сидячие остановки» кофейной,
«сколько тут сидеть» у якоря); точная калибровка — вопрос бэклога, у движка это
открытый параметр, а не спрятанная константа.

## 7. Порядок остановок

- **NN** по матрице минут: от старта, каждый раз ближайший непосещённый.
- **2-opt**: разворот сегментов, принимается только строгое улучшение
  (инвариант теста: 2-opt ≤ NN). Проходы, пока есть улучшение. Разворот
  оценивается **полным пересчётом** стоимости кольца/пути: матрицы пеших
  времён асимметричны (светофоры, переходы), классическая дельта-формула верна
  только для симметричных; k ≤ 6 делает пересчёт дешевле анализа.
- **Петля**: кольцо, стартовая вершина фиксирована (позиция 0), стоимость
  включает замыкающую ногу к старту.
- **А→Б**: оба конца фиксированы, 2-opt только по внутренним вершинам
  (классический path-2-opt: разворот `i..j` меняет рёбра `(i−1,i)` и `(j,j+1)`).
- **Зеркало кольца**: 2-opt видит только времена и слеп к геометрии — при
  равной стоимости два зеркальных обхода для него неотличимы, но один может
  возвращаться по той же улице. Гейт улиц (§8) проверяется на реальных ногах,
  поэтому при его провале движок собирает ноги и для обратного порядка
  (стоимость ≤ текущей) и оставляет вариант с большим числом пройденных
  гейтов. На идеальном плане лишних вызовов роутинга нет.

`null`-ребро = ∞: NN его не выбирает при наличии альтернативы, 2-opt сходится
к конечному кольцу; недостижимая конфигурация отбрасывает вариант (§4.4).

## 8. Гейты качества → `gateReport { gate, pass, detail }`

| gate | условие pass | detail (пример) |
|---|---|---|
| `budget` | `0.9·B ≤ total ≤ 1.1·B` | «67 мин против бюджета 60 (+12%)» |
| `anchors` | остановок ≥ 2 и у каждой непустая причина | «3 якоря, причины заданы» |
| `long_legs` | каждая нога ≤ 25 мин | «максимальная нога 18 мин» |
| `loop_no_repeat_street` | ни одна пара ног не совпадает по улице (только петля) | «повторов улиц нет» |

Ноги > 25 мин без остановки запрещены метрикой; в А→Б это же означает, что
двигок обязан вставить якорь в длинный перегон, если кандидат есть.

**Эвристика «не по той же улице»** (выбор задокументирован): для каждой пары
ног петли обе полилинии прореживаются до ≤ 64 точек; доля точек короче ноги,
лежащих в 30 м от полилинии другой ноги, > 0.6 → гейт падает.
30 м — коридор одной улицы (проезжая часть + тротуары + джиттер роутинга);
0.6 — «большая часть ноги переиспользована», мелкие перекрёстки на светофорах
не наказываются. O(L²·s²) ≈ 0.2 млн дешёвых операций — см. §4. Для А→Б гейт
не применяется (общий участок у старта легален).

## 9. Причины якорей (reason)

Строка по-русски **только из фактов выбора**, приоритет факта:

1. «лучший скор категории „X“ в коридоре/радиусе» — кандидат возглавляет свою
   категорию в шорт-листе;
2. «высокий рейтинг (4.6)» — `rating ≥ 4.5`;
3. «минимальный крюк с линии маршрута (120 м)» / «минимальный крюк от старта»;
4. база: «входит в зону прогулки по весу категории „X“».

Факты детерминированы, значит reason детерминирован — одинаковое состояние
кандидатов даёт одинаковую строку. Гейт `anchors` требует непустой причины у
каждого якоря.

## 10. Скор альтернативы

```
score = Σ weight(category) по выбранным якорям − 1.0 · (число ног > 25 мин)
```

Штраф 1.0 — один «средний» вес за каждую длинную ногу; веса предполагаются
единичного масштаба (0–5), каллибровка — вместе с каллибровкой весов архетипов.
Сортировка альтернатив: `(все гейты pass) desc → score desc → totalMinutes asc`
— детерминированный тотальный порядок.

## 11. Альтернативы через джиттер

3 варианта: базовый + 2 с сидированным джиттером (mulberry32, фиксированные
сиды 1 и 2 — детерминизм: тот же вход → те же планы, никакого `Math.random`):

| параметр | вар. 0 | вар. 1 | вар. 2 |
|---|---|---|---|
| делитель радиуса петли / множитель ширины коридора | 4 / 1.0 | 3.4 / 1.3 | 5 / 0.75 |
| веса категорий | 1.0× | ×(1 + 0.25·(2·rng−1)) | ×(1 + 0.25·(2·rng−1)), сид 2 |

Джиттер весов меняет ранжирование шорт-листа, гео-джиттер — размер зоны:
варианты действительно разные, но все проходят одинаковые гейты.

## 12. Failure modes

| код | когда | политика |
|---|---|---|
| `INVALID_INPUT` | плохие координаты, бюджет ≤ 0, `isLoop=false` без `end`, пустые веса, скорость вне (0,15] | отказ до любых вызовов порта |
| `NOT_ENOUGH_TIME` | даже минимальный план (§4.5) > 1.1×бюджета | отказ, а не мусорный план |
| `NO_CANDIDATES` | после зоны/деградации живых кандидатов нет (или < 2 для петли) | отказ с деталью |
| `NO_ROUTE` | порт бросил на старт→финиш (А→Б) / все варианты упали на ногах | отказ |
| деградация | `null`-ячейки матрицы | кандидат исключается молча — «честная деградация» ADR-001 |

План с упавшим гейтом может вернуться (сортировка поднимет проходящие), кроме
случаев из таблицы выше. Инвариант: **план никогда не отбирается дороже
1.1×бюджета** — превышение отсекается на подборке (по матрице); финальная цифра
считается по реальным ногам роутинга, расхождение с матрицей ловит гейт
`budget`. Недобор ниже 0.9×бюджета виден в `gateReport.detail`, а не спрятан.

## 13. Детерминизм

Никаких `Date.now`, `Math.random`, порядка обхода словарей, зависящего от
вставки. Единственный источник недетерминизма — порт; в тестах он фейковый
(§14). Повторный вызов `createWalkPlan` с тем же входом и тем же портом даёт
бит-в-бит тот же результат.

## 14. Тестовая стратегия (всё оффлайн)

**FakeRoutingPort на сетке-городе** (фикстура `__tests__/gridCity.ts`):
манхэттенская сетка улиц с шагом 500 м; время ноги = манхэттенское расстояние /
скорость, полилиния — Г-образный путь по сетке; «острова» (помеченные точки)
не связаны с городом — матрица честно возвращает `null`. Синтетика задокументирована
в шапке файла: реальный город отличается длиной ног, а не топологией задачи.

Проверки:

1. Петля и А→Б: бюджет ≤ 1.1×B всегда; гейты согласованы с фактами плана;
   причины непусты; петля замыкается (первая и последняя точка ног — старт).
2. Случайные сиды (120 прогонов): инвариант «не дороже 1.1×B», консистентность
   `gateReport` (пересчёт тем же кодом гейтов), сходимость тоталов; детерминизм —
   два прогона с тем же сидом совпадают.
3. 2-opt ≤ NN по времени на случайных конфигурациях (нулевая дельта на сетке).
4. Отказы: крошечный бюджет → `NOT_ENOUGH_TIME`; пустая зона → `NO_CANDIDATES`;
   остров-кандидат не попадает в план (деградация по `null`); А→Б через реку
   без моста → `NO_ROUTE`.
5. Гейт «та же улицы»: на полилиниях-дублях падает, на независимых — нет.
6. Альтернативы: ≤ 3, отсортированы, различаются скором (джиттер весов живой).

## 15. Открытые вопросы

1. Калибровка stay-таблицы и весов — нужны данные реальных прогулок.
2. `null` между якорями в плотной сети — когда порт даёт частичную матрицу:
   сейчас ребро ∞, возможно стоит разрешить «исключить якорь, если он изолирован»
   до заказа ног (мелкая оптимизация числа route-вызовов).
3. Погода/тень/indoor — скоринг поверх маршрута по ADR-001; в движок входит
   через веса категорий и выбор кандидатов, отдельных параметров пока нет.
4. «Остановка работает/актуальна в момент прогулки» — пятый критерий
   PRODUCT.md — требует часов работы (OSM `opening_hours`) в GeoPlace; в срезе
   движка этих данных нет, гейт появится в слое карточек/скоринга.
