# Дизайн: движок прогулок `src/lib/walk`

> Реализация ТЗ из `docs/PRODUCT.md` (раздел «Метрика хорошей прогулки» — гейты).
> Границы: чистый детерминированный движок. Ни UI, ни сети, ни хранения —
> движок получает готовых кандидатов и порт маршрутизации, выдаёт план.

## 1. Роль и границы

```
UI / server actions ──(GeoPlace[])──┐
                                    ▼
                         createWalkPlan(input, ports)
                                    │  ports: matrix(sources, targets), route(waypoints)
                                    ▼
                         WalkPlanResult (3 альтернативы | честный отказ)
```

Движок **не знает**, откуда кандидаты (Overpass, Mongo-дамп) и кто роутит
(OSRM, OpenRouteService, фейк). Он только комбинирует факты.

## 2. Контракт данных и порты

Локальные структурные типы в `src/lib/walk/types.ts` — **без импорта
`lib/geo/types`** (кроме документации). TS-структурность делает их взаимно
совместимыми: `GeoPlace[]` передаётся как `WalkPlace[]` без адаптера, а любой
`GeoProvider` удовлетворяет `WalkRoutingPort`.

| Локальный тип | Структурный двойник в geo/types | Отличия |
|---|---|---|
| `WalkLatLng = [number, number]` | `LatLng` | нет — порядок `[lat, lng]`, единицы: метры и секунды (правило 5 ADR-001) |
| `WalkPlace` | `GeoPlace` | только поля, нужные движку (`id, name, category, coordinates, rating?`); лишние поля источника просто игнорируются |
| `WalkMatrixCell` | `MatrixCell` | `null`-ячейки = недостижимо пешком — контракт обязателен |
| `WalkRouteSegment` | `RouteSegment` | `source` — необязательная строка |
| `WalkRoutingPort` | `GeoProvider` (срез) | только `matrix` + `route`; чанкинг ≤40 точек — забота порта, не движка |

```ts
interface WalkRoutingPort {
  /** Маршрут по реальным улицам. Бросает при недостижимости. */
  route(req: { waypoints: WalkLatLng[] }): Promise<WalkRouteSegment>;
  /** Плоская матрица ячеек; null = недостижимо. */
  matrix(sources: WalkLatLng[], targets: WalkLatLng[]): Promise<WalkMatrixCell[]>;
}
```

Почему `route` принимает `{ waypoints }`, а не сам массив: так `GeoProvider`
совместим с портом по строгой контравариантности аргумента (`RouteRequest`
допускает лишнее опциональное поле `alternatives`), и адаптер не нужен.

## 3. Вход / выход

```ts
interface WalkInput {
  start: WalkLatLng;
  end?: WalkLatLng;        // обязателен при isLoop = false (режим А→Б)
  budgetMinutes: number;   // > 0; первое ограничение генератора
  categoryWeights: Record<string, number>; // вес категории; отсутствие/<=0 = категория не нужна
  candidates: WalkPlace[];
  isLoop: boolean;
  walkingSpeedKmh?: number;               // default 4.5
  categoryStayMinutes?: Record<string, number>; // переопределение таблицы stay
}

type WalkPlanResult =
  | { ok: true; plans: WalkPlan[] }              // до 3, отсортированы
  | { ok: false; failure: WalkFailure };
```

Расширение относительно ТЗ: добавлено поле `end?` — режим «А→Б, но красиво» по
PRODUCT.md невозможен без финиша, а коридор считается именно до него. `isLoop =
false` без `end` → `INVALID_INPUT`.

## 4. Алгоритм по шагам

1. **Валидация** (`INVALID_INPUT`): координаты конечны, `budgetMinutes > 0`,
   `speed ∈ (0, 15]`, `categoryWeights` непуст, `end` присутствует при
   `isLoop = false`.
2. **Зона поиска** (см. §5): коридор к финишу (А→Б) или радиус (петля).
3. **Отбор кандидатов**: фильтр по зоне + вес категории > 0 → скор → **cap 60**.
4. **Матрица**: один вызов `matrix(все_точки, все_точки)` — старт, финиш
   (А→Б) и шорт-лист. Кандидаты с `null`-ячейкой к старту (и к финишу в А→Б)
   выбрасываются — честная деградация. Между якорями `null` = ребро бесконечной
   стоимости: NN/2-opt его обходят; если избежать не удалось — вариант плана
   отбрасывается.
5. **Отказы на дешёвых проверках** до всякой сборки:
   - без порта, нижние оценки: любой пеший путь ≥ прямой линии, поэтому
     А→Б `прямая/скорость > 1.1×бюджета` → `NOT_ENOUGH_TIME`; петля —
     `min(2·прямая/скорость + stay)` по кандидатам > 1.1×бюджета →
     `NOT_ENOUGH_TIME`;
   - по матрице: А→Б — прямая ячейка старт→финиш `null` → `NO_ROUTE`,
     время > 1.1×бюджета → `NOT_ENOUGH_TIME`; петля —
     `min(2·t(старт,c) + stay(c))` по живым кандидатам > 1.1×бюджета →
     `NOT_ENOUGH_TIME`; живых кандидатов < 2 → `NO_CANDIDATES`
     (2 якоря — минимум продуктовой метрики, мусорный план из одного якоря не
     отдаём; в А→Б чистый маршрут без якорей полезен сам по себе — план
     возвращается с честно упавшим гейтом `anchors`).
6. **Подбор количества остановок** (жадный): ранжированный шорт-лист
   просматривается по порядку; кандидат добавляется, если план с ним
   ≤ 1.1×бюджета (порядок пересчитывается, стоимость — по матрице), иначе
   пропускается (дорогой кандидат не блокирует дешёвых следующих). Верхняя
   граница — `MAX_STOPS = 6` (PRODUCT: 2–4 остановки, +запас для длинных
   бюджетов; гейт `anchors` требует ≥ 2).
7. **Порядок обхода**: NN по матрице минут + 2-opt (§7).
8. **Реальные ноги**: для финального порядка — `route()` на каждую ногу.
   Геометрия и время ног — от роутинга (PRODUCT: «улицы, а не прямые линии»).
   Упавший `route()` → вариант плана отбрасывается. Планирование считается по
   матрице, финальный бюджет — по метрикам реальных ног (согласованы в рамках
   одного провайдера).
9. **Гейты** (§8) → `gateReport`. **Причины якорей** (§9). **Скор** (§10).
10. **Альтернативы**: шаги 2–9 повторяются на 3 вариантах параметров (§11),
    результаты сортируются: все гейты pass → выше скор → короче.

### Сложность

| Шаг | Стоимость | Практика |
|---|---|---|
| Отбор + скор | O(n) | n — входные кандидаты |
| Матрица | O(m²) ячеек, m ≤ 62 | чанкинг ≤40 — на стороне порта; ~4 запроса ORS |
| Жадный подбор | O(m · k²) | k ≤ 6: NN+2-opt на каждой примерке ≈ 60·36 = 2 160 оп. |
| 2-opt | O(k²) на проход, ≤ k проходов | микро |
| Гейт «та же улица» | O(L² · s²), L ≤ 7 ног, s ≤ 64 точки | ≈ 200 тыс. дешёвых оп. |

Всё — миллисекунды на клиентских мощностях; сеть (матрица+ноги) доминирует.

## 5. Зона поиска

**А→Б — коридор.** Ширина от прямой `start→end`:
`W = clamp(0.3 · d, 300 м, 1500 м)`. Отбор: расстояние точка→отрезок ≤ W.
Почему отрезок, а не конус направления: конус из `placeRanking.ts` считает
dot product по сырым градусам — 1° широты ≠ 1° долготы в метрах, конус
перекошен вдоль параллели, и у цели сбоку он вообще вырождается. Расстояние до
осевой линии — та же идея без искажения и без произвольного угла раствора.

**Петля — радиус.** `R = v·(0.6·budget)/4`:
`0.6·budget` — ходячая доля бюджета (40% резервируем под stay и кривизну улиц),
делитель 4 соответствует кольцу через якорь на противоположной стороне
(длина кольца ≈ 4·R для ромбовидной формы). Пример: 60 мин → 36 мин ходьбы →
2.7 км пешком → R ≈ 0.7 км. Радиус — эвристика зоны, не граница маршрута:
реальные ноги всё равно считает роутинг, а бюджет проверяется после.

Проекция для метров: локальная равнопромежуточная (`equirectangular`) вокруг
центра зоны — на масштабе города (<10 км) ошибка << 1%.

## 6. Время стоянок (stay)

Бюджет = Σ ходьба + Σ stay. Stay берётся из таблицы по категории
(переопределяется `categoryStayMinutes`):

| категория | park | museum | cafe | restaurant | bar | viewpoint | attraction | cinema | shopping | прочее |
|---|---|---|---|---|---|---|---|---|---|---|
| минут | 25 | 45 | 20 | 40 | 30 | 15 | 25 | 90 | 40 | 20 |

Числа — продуктовые согласующие PRODUCT («1–2 сидячие остановки» кофейной,
«сколько тут сидеть» у якоря); точная калибровка — вопрос бэклога, у движка это
открытый параметр, а не спрятанная константа.

## 7. Порядок остановок

- **NN** по матрице минут: от старта, каждый раз ближайший непосещённый.
- **2-opt**: разворот сегментов, принимается только строгое улучшение
  (инвариант теста: 2-opt ≤ NN). Проходы, пока есть улучшение. Разворот
  оценивается **полным пересчётом** стоимости кольца/пути: матрицы пеших
  времён асимметричны (светофоры, переходы), классическая дельта-формула верна
  только для симметричных; k ≤ 6 делает пересчёт дешевле анализа.
- **Петля**: кольцо, стартовая вершина фиксирована (позиция 0), стоимость
  включает замыкающую ногу к старту.
- **А→Б**: оба конца фиксированы, 2-opt только по внутренним вершинам
  (классический path-2-opt: разворот `i..j` меняет рёбра `(i−1,i)` и `(j,j+1)`).
- **Зеркало кольца**: 2-opt видит только времена и слеп к геометрии — при
  равной стоимости два зеркальных обхода для него неотличимы, но один может
  возвращаться по той же улице. Гейт улиц (§8) проверяется на реальных ногах,
  поэтому при его провале движок собирает ноги и для обратного порядка
  (стоимость ≤ текущей) и оставляет вариант с большим числом пройденных
  гейтов. На идеальном плане лишних вызовов роутинга нет.

`null`-ребро = ∞: NN его не выбирает при наличии альтернативы, 2-opt сходится
к конечному кольцу; недостижимая конфигурация отбрасывает вариант (§4.4).

## 8. Гейты качества → `gateReport { gate, pass, detail }`

| gate | условие pass | detail (пример) |
|---|---|---|
| `budget` | `0.9·B ≤ total ≤ 1.1·B` | «67 мин против бюджета 60 (+12%)» |
| `anchors` | остановок ≥ 2 и у каждой непустая причина | «3 якоря, причины заданы» |
| `long_legs` | каждая нога ≤ 25 мин | «максимальная нога 18 мин» |
| `loop_no_repeat_street` | ни одна пара ног не совпадает по улице (только петля) | «повторов улиц нет» |

Ноги > 25 мин без остановки запрещены метрикой; в А→Б это же означает, что
двигок обязан вставить якорь в длинный перегон, если кандидат есть.

**Эвристика «не по той же улице»** (выбор задокументирован): для каждой пары
ног петли обе полилинии прореживаются до ≤ 64 точек; доля точек короче ноги,
лежащих в 30 м от полилинии другой ноги, > 0.6 → гейт падает.
30 м — коридор одной улицы (проезжая часть + тротуары + джиттер роутинга);
0.6 — «большая часть ноги переиспользована», мелкие перекрёстки на светофорах
не наказываются. O(L²·s²) ≈ 0.2 млн дешёвых операций — см. §4. Для А→Б гейт
не применяется (общий участок у старта легален).

## 9. Причины якорей (reason)

Строка по-русски **только из фактов выбора**, приоритет факта (M5 волны
human design: без тавтологий и языка скоринга — «Кофейня · Лучший „кафе“
поблизости» читалось как тавтология, «лучший скор категории» — движковым
жаргоном):

1. «Лучший выбор рядом» — кандидат возглавляет свою категорию в шорт-листе;
2. «Прямо по пути (~120 м)» — кандидат самый близкий к линии/старту;
3. «Стоит небольшого крюка (~180 м)» — остальное: позиция честно названа
   крюком от линии, в метрах;
4. «, рейтинг 4.6» — дополнение к голове при `rating ≥ 4.5`.

EN-твин (`reasonEn`) — параллельная ветка тех же фактов ("A top pick nearby",
"Right on the way (~120 m)", "Worth a short detour (~180 m)").

Все формулы **самодостаточны**: имя категории в строку не вписывается, поэтому
`uiAdapter` выводит `reasonStandalone`, и карточка рендерит причину без префикса
категории (имя и иконка уже называют место). Легаси-строки старых планов
(«лучший скор категории „X“ в коридоре/радиусе», «Лучший «кафе» поблизости»,
"The best cafe around") распознаются маркерами `uiAdapter.isReasonStandalone`
и рендерятся с префиксом, как раньше.

Факты детерминированы, значит reason детерминирован — одинаковое состояние
кандидатов даёт одинаковую строку. Гейт `anchors` требует непустой причины у
каждого якоря.

## 10. Скор альтернативы

```
score = Σ weight(category) по выбранным якорям − 1.0 · (число ног > 25 мин)
```

Штраф 1.0 — один «средний» вес за каждую длинную ногу; веса предполагаются
единичного масштаба (0–5), каллибровка — вместе с каллибровкой весов архетипов.
Сортировка альтернатив: `(все гейты pass) desc → score desc → totalMinutes asc`
— детерминированный тотальный порядок.

## 11. Альтернативы через джиттер

3 варианта: базовый + 2 с сидированным джиттером (mulberry32, фиксированные
сиды 1 и 2 — детерминизм: тот же вход → те же планы, никакого `Math.random`):

| параметр | вар. 0 | вар. 1 | вар. 2 |
|---|---|---|---|
| делитель радиуса петли / множитель ширины коридора | 4 / 1.0 | 3.4 / 1.3 | 5 / 0.75 |
| веса категорий | 1.0× | ×(1 + 0.25·(2·rng−1)) | ×(1 + 0.25·(2·rng−1)), сид 2 |

Джиттер весов меняет ранжирование шорт-листа, гео-джиттер — размер зоны:
варианты действительно разные, но все проходят одинаковые гейты.

## 12. Failure modes

| код | когда | политика |
|---|---|---|
| `INVALID_INPUT` | плохие координаты, бюджет ≤ 0, `isLoop=false` без `end`, пустые веса, скорость вне (0,15] | отказ до любых вызовов порта |
| `NOT_ENOUGH_TIME` | даже минимальный план (§4.5) > 1.1×бюджета | отказ, а не мусорный план |
| `NO_CANDIDATES` | после зоны/деградации живых кандидатов нет (или < 2 для петли) | отказ с деталью |
| `NO_ROUTE` | порт бросил на старт→финиш (А→Б) / все варианты упали на ногах | отказ |
| деградация | `null`-ячейки матрицы | кандидат исключается молча — «честная деградация» ADR-001 |

План с упавшим гейтом может вернуться (сортировка поднимет проходящие), кроме
случаев из таблицы выше. Инвариант: **план никогда не отбирается дороже
1.1×бюджета** — превышение отсекается на подборке (по матрице); финальная цифра
считается по реальным ногам роутинга, расхождение с матрицей ловит гейт
`budget`. Недобор ниже 0.9×бюджета виден в `gateReport.detail`, а не спрятан.

## 13. Детерминизм

Никаких `Date.now`, `Math.random`, порядка обхода словарей, зависящего от
вставки. Единственный источник недетерминизма — порт; в тестах он фейковый
(§14). Повторный вызов `createWalkPlan` с тем же входом и тем же портом даёт
бит-в-бит тот же результат.

## 14. Тестовая стратегия (всё оффлайн)

**FakeRoutingPort на сетке-городе** (фикстура `__tests__/gridCity.ts`):
манхэттенская сетка улиц с шагом 500 м; время ноги = манхэттенское расстояние /
скорость, полилиния — Г-образный путь по сетке; «острова» (помеченные точки)
не связаны с городом — матрица честно возвращает `null`. Синтетика задокументирована
в шапке файла: реальный город отличается длиной ног, а не топологией задачи.

Проверки:

1. Петля и А→Б: бюджет ≤ 1.1×B всегда; гейты согласованы с фактами плана;
   причины непусты; петля замыкается (первая и последняя точка ног — старт).
2. Случайные сиды (120 прогонов): инвариант «не дороже 1.1×B», консистентность
   `gateReport` (пересчёт тем же кодом гейтов), сходимость тоталов; детерминизм —
   два прогона с тем же сидом совпадают.
3. 2-opt ≤ NN по времени на случайных конфигурациях (нулевая дельта на сетке).
4. Отказы: крошечный бюджет → `NOT_ENOUGH_TIME`; пустая зона → `NO_CANDIDATES`;
   остров-кандидат не попадает в план (деградация по `null`); А→Б через реку
   без моста → `NO_ROUTE`.
5. Гейт «та же улицы»: на полилиниях-дублях падает, на независимых — нет.
6. Альтернативы: ≤ 3, отсортированы, различаются скором (джиттер весов живой).

## 15. Открытые вопросы

1. Калибровка stay-таблицы и весов — нужны данные реальных прогулок.
2. `null` между якорями в плотной сети — когда порт даёт частичную матрицу:
   сейчас ребро ∞, возможно стоит разрешить «исключить якорь, если он изолирован»
   до заказа ног (мелкая оптимизация числа route-вызовов).
3. Погода/тень/indoor — скоринг поверх маршрута по ADR-001; в движок входит
   через веса категорий и выбор кандидатов, отдельных параметров пока нет.
4. «Остановка работает/актуальна в момент прогулки» — пятый критерий
   PRODUCT.md — требует часов работы (OSM `opening_hours`) в GeoPlace; в срезе
   движка этих данных нет, гейт появится в слое карточек/скоринга.

- **Лестница деградации** `fallback.ts` → `loopThrough.ts` → `streetLoop.ts`
  (дополнение к §12): строгий движок → петля через лучших кандидатов →
  чистая уличная петля. Перекрытие улиц считает `internal/geo.ts`
  (`maxStreetOverlap`, коридор 30 м, порог 0.6). `INVALID_INPUT`
  деградацией не лечится — отсекается в оркестраторе. Это реализация
  принципа PRODUCT.md «почти всегда прогулка».
- **Замена остановки** `replaceStop.ts`: меняется один сегмент плана, ноги
  соседей переиспользуются; причины выживших остановок едут с клиента как
  факты прошлого скоринга и не пересчитываются (контекст мог измениться,
  пул замены их не содержит).
- **Мемо-порт** `memoPort.ts`: FIFO-кэш route/matrix поверх
  `WalkRoutingPort` — гасит дубли запросов между тремя вариантами и
  зеркалом кольца. Структурная совместимость с GeoProvider сохраняется.
- **Адаптер в UI** `uiAdapter.ts`: `WalkPlan` движка → UI-карточка
  (`components/walk/types.ts`); скоринговые причины из `quickPipeline`
  ложатся поверх якорной причины движка.
- **Шаринг/сохранение** `shareCodec.ts`: UI-план → исторический формат
  `routeCodec` v2 (ссылка `?r=…` = маршрут) и ссылка «Идти» в Яндекс.Карты
  (`rtt=pd`); чистая петля без остановок кодируется сэмплом геометрии
  (≤10 точек).
- **Гейт «работает сейчас»** — закрывает §15.4. Движок время не знает
  (границы §1 соблюдены): enforcement живёт в
  `quickPipeline.scoreCandidatePool`. `opening_hours` парсит
  `lib/places/hours.ts` (`evaluateOpeningHoursDetailed`, сшивка суток через
  полночь); закрытые кандидаты отсеваются, пока живых ≥ 12
  (`MIN_ALIVE_FOR_FILTER`, иначе честная деградация); «скоро закроется»
  (≤30 мин) — штраф −0.10 в скоринге (docs/vibes.md §5.3); бейдж
  «Открыто · до HH:MM» — в таймлайне (`StopRow`) и карточке пина.
- **Обзорная зона** `sightseeing` — архетип входа «Новый город»
  (docs/vibes.md §3.5.1). Движку не нужен новый код: это другой профиль
  весов и таймингов, зона считается так же (петля от произвольной точки).
  Ревизия 2026-11-18: UI-вход «Новый город» убран (PRODUCT.md, «Два сценария
  входа»); архетип сохранён в vibes как запасной профиль — движок его не
  удаляет и не различает.

## 17. Волна «Прогулка, а не кратчайший путь» (ревизия 2026-11-17)

ТЗ и решения — docs/walk-loop-quality.md; здесь зафиксировано, как механики
волны легли на инварианты §1–16. §1–15 не менялись.

- **Коридор бюджета.** Бюджет — коридор `FLOOR_SHARE·B = 0.9·B … 1.1·B`
  (§12 дополнен нижней границей). После реальных ног строгий движок зовёт
  `fillToFloor` (createWalkPlan.ts): сначала добор остановками из пула с той
  же политикой, что у жадного набора (maxStopsForBudget, кап категории, gap),
  вставка по минимальной дельте матрицы (одна нога → две), оценка с запасом
  `SAFETY_MARGIN_SHARE = 0.05·B`; затем via-удлинение длиннейших ног
  ≤ `MAX_LEG_MINUTES − 2` мин через перпендикулярный офсет
  `h = √(Δ·(2D+Δ))/2` (internal/geo.viaOffsetForExtraMeters) и tune-цикл
  (GROW 1.3 / SHRINK 0.85, ≤3 попыток на ногу, ≤2 via-ног на план). Реальный
  total после добора проверяется на потолок: вылетел — откат последнего добора
  и стоп (§12 — инвариант). Не дотянули — план возвращается как есть,
  недобор видит гейт `budget`; фиктивных минут нет. L2 (`loopThrough`) и
  L3 (`streetLoop`) добором не трогаются — «что есть, то есть» (§16 лестница
  без изменений). Побочно: `splitPolylineByWaypoints` теперь честно возвращает
  `waypoints.length + 1` сегментов и на пустой полилинии (контракт файла).
- **Эскалация пула — на action-уровне.** Чистый предикат `isUnderfloor(plan,
  budget)` (экспортируется): экшен `buildQuickWalk` после сборки, если лучший
  план недобрал до пола, один раз повторяет `collectCandidates` с
  `SECOND_WAVE_MULTIPLIER` и пересобирает; вторая волна не дотянула —
  возвращается первая. Движок про Overpass не знает — граница слоёв §1.
- **Ноги с альтернативами.** `WalkRoutingPort.routeAlternatives?` — до трёх
  маршрутов по 2 вейпоинтам, основной первым; memoPort обязан пробросить
  (отдельный кэш, дисковый kind `route-alt`, TTL как у route). CloudProvider
  реализует метод через ORS `alternative_routes` (target_count ≤ 3,
  share_factor 0.6, weight_factor 1.3, только 2 вейпоинта); кэш-ключ route
  теперь включает alternatives. Деградация честная: 400/2011, пустой набор,
  одна
  фича — «альтернатив нет», лег строится обычным `route`; квота/лежка
  (429/5xx) бросаются как есть. Движок запрашивает альтернативы для ног с
  матричной оценкой > `LEG_ALT_MIN_MINUTES = 8` при общем капе
  `MAX_ROUTE_CALLS = 24` вызовов порта на сборку (сверх капа — обычный
  route). Выбор — `chooseLegVariant` (чистая, экспортирована): минимум
  пересечения с принятыми ногами (`fractionWithinCorridor`, коридор 30 м),
  при равном — длиннейший, влезающий в потолок 1.1·B; победитель помечается
  `WalkLeg.routeVariant: 'alt'`. `replaceStop`, trio-матрица, L2/L3 — на
  простом route; альтернативная геометрия не переживает замену (зафиксировано
  как приемлемое).
- **Воронка без проксимити-перекоса.** Скор отбора — общая
  `candidateScore(weight, rating, proximity, zone)` с
  `PROXIMITY_WEIGHT = 0.25` (было 1.0 — близость доминировала): единая
  формула для `selectCandidates` и вариантного отбора. Нарезку шорт-листа
  ведёт экшен: пул фильтруется минимальной зоной вариантов
  (`minimalLoopZoneMeters` — самый узкий радиус ZONE_VARIANTS, иначе узкий
  вариант умирает NO_CANDIDATES) и режется `diversifyByAzimuth` —
  раунд-робин по 8 секторам азимута (equirect-проекция), `SECTOR_CAP = 6`
  на сектор; разреженный пул добирается внешними кандидатами по скору.
  Пул замены диверсифицируется так же до `REPLACE_CANDIDATE_CAP`.
  Overpass: `limit` на категорию 12 → 20, пороги эскалации
  `overpass-places` параметризованы долей лимита (при 12 сходятся к прежним
  8/12).
- **Честность в UI.** `UiWalkPlan.gatesSummary` — плоский массив отчётов
  гейтов `{ name, pass, detail }`; поле объявлено аддитивной декларацией в
  uiAdapter (UI-слой волной не трогался — рендер с guard'ом за следующей
  волной). `GATE_NOTES` — человекочитаемые заметки для недобора и
  walk_share, тексты синхронизированы со словарями
  (`WalkUI.gateNoteUnderfloor` / `gateNoteWalkShare`, тест uiAdapter).
  Экшен замены принимает `currentGatesSummary`: база фолбэка считается из
  фактов гейтов, а не из хардкода «петля = 4»; `currentGatesPassed`
  остаётся фолбэком для старых клиентов.
- **Тайбрейкер покрытия петли.** §10 дополнен: сортировка вариантов —
  гейты pass → скор → `loopCoverage` (только петля) → короче. Площадь
  считается по сырой полилинии через выпуклую оболочку (монотонная цепочка
  Эндрю) + shoelace — знаковая алгебраическая площадь на «восьмёрке»
  схлопнулась бы, оболочка этому не подвержена; нулевая площадь
  (out-and-back, пустая геометрия) уводит сравнение в totalMinutes.

## 18. Волна «Улицы с характером» (ревизия 2026-11-17)

ТЗ и решения — docs/street-interest-wave.md; здесь зафиксировано, как механики
легли на инварианты §1–17. §1–15 не менялись.

- **Данные.** `GeoProvider.fetchStreetFeatures?` (аддитивное расширение
  контракта, ADR-001) — один Overpass-запрос 5 классов фич union'ом (green,
  water, pedestrian, viewpoint, art) с statement-bbox и клипом геометрии
  вывода `out geom (s,w,n,e)`; радиус клампится в [500, 3000] м, свой
  клиентский таймаут 20 с (не делит overpassMs с POI). Клиентские капы:
  элементы > 3000 или сырые точки > 50 000 → частичная деградация (только
  ядро water/green/pedestrian) или null. Парсер с нуля: node → точка,
  way → линия/контур (децимация ≤64 точек, площадь замкнутого кольца),
  relation → outer-кольца members с дедупом против way-фич, inner (острова)
  мимо; безымянные фичи не отбрасываются. Конверсия в структурные двойники
  `WalkStreetFeature`/`WalkStreetHints` (walk/types.ts, без импортов lib/geo —
  §2) — на границе в quickPipeline.
- **Интерес-модель.** `scoreSectors` (lib/vibes/streetInterest) — 8 азимутальных
  секторов, конвенция pinned (роза↔проекция, 45°; нюанс: угловой параметр
  розы — НЕ компасный азимут, сектор считается от самой точки через
  `azimuthRad`). Вклад фичи = база kind (`STREET_FEATURE_KIND_WEIGHTS`, единая
  с S5) × архетипный множитель (`Archetype.streetInterest`, docs/vibes.md
  §3.7) × мягкая близость × лог-размер полигона. Присвоение сектору — по
  вершинам (крупный парк честно делит вклад); `attractionPoint` — проекция
  старта на контур лучшей фичи сектора (`closestPointOnPolyline`), не вершина.
- **Умная роза (L3).** Снап к attraction-точкам живёт ВНУТРИ `buildWaypoints`
  (tune перестраивает вейпоинты только через неё — снап не стирается
  ×1.3/×0.85; радиус-джиттер на снапнутой точке не живёт). Условия: сектор
  по конвенционному азимуту геометрической точки, `interest ≥ 0.35`, отклонение
  ≤ 30% радиуса. Дедуп attraction-точек — энфорс `MIN_ANGLE_GAP_DEG` между
  снапнутыми (слабейший по интересу откатывается к геометрии). Отказ route со
  снапнутыми точками → один ретрай варианта с геометрией; матрица в L3 не
  участвует, кап `MAX_ROUTE_CALLS` имеет запас. План с ≥2 снапнутыми секторами
  помечается `streetInterest: true` вместо `loop-only` (union уровней не
  расширялся); заметка «Петля по характерным улицам района» в uiAdapter,
  тексты ru/en в коде, sync-тест uiAdapter.
- **Микро-стопы и решение о минутах (B2).** `WalkLeg.microNotes` — точки kind
  viewpoint/art и берега воды (ближайшая к пути вершина) в буфере 60 м от
  полилинии ноги после финального роутинга, ≤2 на ногу, отсорт по близости.
  Минуты считает движок ДО `evaluateGates`: стопы цепляются к ногам, добавляя
  MICRO_STOP_MINUTES = 2 в `durationMinutes` ноги — totals пересчитываются
  после, гейты и карточка видят честный total. Кап на план
  Σmicro ≤ min(4, max(0, 1.1·B − total)) — постфактум-добавление запрещено
  (иначе карточка показала бы total > 1.1·B при gatesPass=true). Микро-минуты
  идут в totals как walk («шаг, взгляд»), не stay — walk_share не перевирается.
  Гейт anchors микро-стопы не засчитывает (stops не трогаются). Дополнение
  к ТЗ: ноги у потолка `MAX_LEG_MINUTES − 2` не получают стопов — +2 минуты
  сломали бы long_legs без пользы. replaceStop переиспользует ноги по ссылке:
  microNotes выживших ног остаются, пересобранных (k, k+1) — исчезают;
  microNotes не переживают и шеринг (shareCodec кодирует stops) —
  задокументированная честная деградация, не баг.
- **Интерес в выборе альтернатив (S5).** Тайбрейкер (б) дополнен: при равном
  непересечении (критерий (а) первичен) побеждает альтернатива с бОльшей
  долей полилинии в буфере `ALT_INTEREST_BUFFER_M = 80` м от green/water/
  pedestrian фич (`fractionWithinAnyCorridor`), при равном интересе —
  длиннейший влезающий, дальше — порядок входа. Перф (C11): bbox-префильтр
  фич вокруг ноги + топ-32 по весу класса (`altInterestPolylinesForLeg`),
  ресемпл 64 один раз на ногу и общий для всех альтернатив.
- **Интеграция (S6/S7).** `fetchStreetInterest` в quickPipeline: отдельный
  «батч из 1» ПОСЛЕ последней категории POI с той же паузой (пик
  конкурентности Overpass остаётся 3), вне ретрай-волны (упал → null).
  Провайдер без метода — тоже null. `WalkInput.streetFeatures/streetHints`
  и `StreetLoopInput.streetHints/streetFeatures` — L3 получает поля явно
  через fallback. Кэш street-features — свой TtlLruCache CloudProvider
  (50 записей, TTL 10 мин, отрицательный 90 с). Деградация: пустой ответ =
  «данных нет» (hasData=false, поля undefined, не пустые массивы) — снапшот-тест
  подтверждает побитовое совпадение планов с прежними.

## 19. Инверсия «улица первична» (ревизия 2026-11-18)

ТЗ владельца: быстрая прогулка вела юзера «по кафе и магазинам — ЛЮДИ ТУДА НЕ
ЗАХОДЯТ НА ПРОГУЛКЕ… я когда гуляю просто иду по улице». До этой ревизии
уличная петля (§18) жила деградацией L3; теперь для всех прогулочных вайбов
она — **первичный путь**, а якоря из POI — гарниш. §1–18 описывают якорь-драйвен
конвейер — он остаётся точным для дождя и А→Б; здесь зафиксирована инверсия.

### 19.1. Два конвейера главного сценария

```
вайб = rain  →  якорь-драйвен (§4–§18 без изменений):
               collectCandidates → createWalkPlan → лестница fallback (L1→L2→L3)
вайб ≠ rain  →  street-first (новый модуль streetFirst.ts):
               collectCandidates (гарниш-пул, отказ поиска ≠ отказ прогулки)
               → buildStreetLoop (умная роза §18) → гарниш 0–2 → добор до коридора
```

Отличие отказов: у якорь-драйвена пустой пул = отказ («рядом не нашлось
интересных мест»); у street-first пустой пул — это 0 якорей-гарниша, а петля
строится всегда, где жив роутер. Отказ street-first — только
`NO_ROUTE` петли (роутер недоступен) или `INVALID_INPUT`.

### 19.2. Сборка петли: варианты-альтернативы

`buildStreetLoop` больше не останавливается на первом чистом варианте: роза
перебирает варианты (§18: квадрат ×4 поворота + треугольник), **до 3 чистых
(перекрытие ≤ порога) собираются в список** — это альтернативы слайдера,
порядок = приоритет перебора (детерминизм §13). Общий кап route-вызовов
`MAX_ROUTE_CALLS = 28` на всю сборку street-first (петли + гарниш): сверх капа
недостроенные варианты не собираются, гарниш не ставится.

Тюнинг-окно длительности петли `MIN_DURATION_SHARE` 0.5 → **0.9**: уличная
петля сама заполняет бюджет (улицы не кончаются — POI кончаются), поэтому её
коридор [0.9, 1.15]·B совпадает с гейтом бюджета. Длина по-прежнему
подгоняется коррекцией радиуса (×1.3 / ×0.85).

### 19.3. Гарниш: якоря в коридоре петли (0–2)

Модуль `garnish.ts`, чистые функции + порт. Алгоритм на каждую петлю:

1. **Коридор.** Кандидат годен, если отклонение его точки от полилинии
   ближайшей ноги ≤ `GARNISH_CORRIDOR_M = 200` (проекция на сегменты ноги,
   `closestPointOnPolyline`). Нога-хозяин — нога с минимальным отклонением.
2. **Порядок.** Сорт по `вес × качество` — `weight(category) · (1 + rating/5)`
   (нерейтингованные не дискриминируются: база качества 1), тайбрейкеры —
   меньшее отклонение, затем порядок входа (скор-порядок экшена). Капы
   категории архетипа (`categoryLimits`, дефолт 2) действуют как у движка.
3. **Бюджет.** Якорь вставляется разрезом ноги-хозяина на две реальные ноги
   (2 route-вызова) только если `новый total ≤ 1.1·B`; оценка до роутинга —
   по прямой с сетевым коэффициентом 1.3. Не влез — пропускается, перебор
   продолжается. `MAX_GARNISH = 2`.
4. **Причины** — переиспользован §9 (`reasons.ts`): `isBestOfCategory` — первый
   в своей категории среди годных коридора; `isClosest` — минимальное
   отклонение среди **выбранных** якорей; `proximityMeters` — отклонение от
   полилинии («Прямо по пути (~120 м)» — честный факт: место в 120 м от петли).
5. Микро-стопы на разрезанных ногах пересобираются (`attachMicroNotes` только
   для двух новых ног — функция мутирует и не идемпотентна); микро-стопы
   остальных ног переживают вставку.

**Резерв под гарниш.** Петля строится на бюджет `B − reserve`, чтобы
сидячая остановка влезала поверх улиц: `reserve = min(stay(лучшего годного
кандидата) + 5, ⌊0.5·B⌋, 45)`, при пустом пуле — 0. Если гарниш не встал
(коридор пуст, всё не влезло) и итог недобрал пола `0.9·B` — **фаза добора**:
петля перестраивается на полный бюджет B (та же роза, те же варианты,
детерминизм; гарниш на ней не ищется — комнате взяться неоткуда). Фаза не
запускается, если гарниш уже стоит: план с якорем и недобором честнее петли
без содержимого (гейт `budget` пометит недобор — `GATE_NOTES.budget` в
карточке объясняет это словами «вышла короче плана»).

Вторая волна поиска (`SECOND_WAVE_MULTIPLIER`, §17 R1.d) street-first не
касается: петля от пула не зависит, а гарниш живёт в коридоре 200 м, куда
шире поиск новых кандидатов почти не приносит.

### 19.4. Гейты уличного плана (§8 дополнен)

`GateFacts.planType?: 'anchored' | 'street'` (по умолчанию `anchored`).
Для `street` набор другой: **без** `anchors` и **без** `long_legs`
(содержание идёт под ногами — «сегмент без остановки» не дефект), плюс новый
гейт интереса:

| gate | условие pass (street) |
|---|---|
| `budget` | total в [0.9, 1.1]·B — как раньше |
| `walk_share` | ходьба ≥ 35% бюджета — как раньше |
| `loop_no_repeat_street` | как раньше |
| `street_interest` | только при `hasData` данных среды: снап-секторов ≥ 2 |

Без данных среды гейт `street_interest` не выпускается (не наказываем план за
то, чего мы не знаем — принцип 5 PRODUCT.md); сам план несёт заметку деградации
(§19.5). `GATE_NOTES.street_interest` — человекочитаемая строка провала для
карточки. У якорь-драйвен планов набор §8 не изменился.

### 19.5. Маркировка плана и лестница (§16 пересобрана)

`WalkPlan` получил `kind?: 'street'` и `streetSnappedSectors?: number`
(факт для гейта и деталей). Лестница теперь двухконвейерная:

- **street-first (outdoor):** петля с данными → петля без данных → отказ.
  Снап ≥ 2 секторов — `streetInterest: true` (заметка в карточке, §18);
  снапа нет при живых данных — план без пометок (среда была, роза мимо не
  легла — обещания не было); данных нет вовсе (`hasData=false` или бандл
  null) — `degraded: { level: 'street-no-data' }` (новый уровень закрытого
  union) с честной заметкой «характер улиц не подгрузился».
- **rainy (якорь-драйвен):** лестница §16 как была — strict → L2
  (`loopThrough`) → L3 (`streetLoop`). L2 **сохранён**: для дождя краевой
  случай «строгий движок отказал (мало якорей в зоне), но лучшие кандидаты
  скелетом петли пригодны» — единственное место, где он вызывается; для
  street-first он не нужен (петля не зависит от кандидатов).
  L3-план дождя по-прежнему помечается `loop-only` (там «интересных мест
  не нашлось» — правда), marking переносится в `fallback.ts` из
  `streetLoop.assemblePlan`.

### 19.6. Замена гарниша (принцип 3 PRODUCT.md)

`replaceStop.ts` дополнен `replaceStreetGarnish`: у street-плана ноги — это
кольцо «старт → вершины розы → якоря → старт», кольцевые вершины выводятся из
`legs[i].from/to`. Замена якоря-гарниша: соседи берутся из кольца, ноги
соседей и вся петля **переиспользуются по ссылке**, перестраиваются только
две ноги к новому кандидату (trio-матрица + бюджет-гард — механика §16).
План должен нести `kind: 'street'` и полные геометрии ног — иначе честный
отказ замены («пересоберите прогулку»), уничтожать розу перестройкой
старт→якорь→старт нельзя. Маркировка `streetInterest`/`degraded` заменой не
сохраняется (прецедент §16 — замена строит новый план без деградационных
помет); `kind` сохраняется. Когда якорей 0 — «Заменить» не рендерится
(нечего менять), «Изменить параметры» живёт как раньше.

### 19.7. UI-заметки (волна «Улицы», ревизия)

- Заметка «почему петля идёт тут» — архетипная: `streetLoopNote(archetypeId)`
  в vibes (vibes.md §3.7) прокидывается экшеном в `enginePlansToUiPlans` и
  рендерится существующей плашкой `StreetInterestNote` (данные → словарь).
- Таймлайн street-плана с якорями показывает и ногу **до** первого якоря
  (`legs[0]`) — для якорь-драйвен планов рендер не меняется.
- `FailedGatesNotes` добавляет строку провала `street_interest`.
- Шеринг: `kind`/`streetSnappedSectors`/микро-стопы в `?w=` не кодируются —
  расшаренный street-план рендерится как обычная петля (задокументированная
  деградация, как microNotes в §18).
