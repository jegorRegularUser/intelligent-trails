# Вайбы и контекст — дизайн скоринга «формулы прогулки»

> Дизайн-документ ветки `feat/vibes-context`. Код в `next-app/src/lib/vibes/**`
> и `next-app/src/lib/weather/**` реализует ровно числа отсюда. Меняется число —
> меняется документ, и наоборот.

Опирается на `docs/PRODUCT.md` («Формула прогулки», «Сценарии-архетипы»,
«Честная деградация»). Зоны: `src/lib/vibes/**`, `src/lib/weather/**`.
Старый `src/utils/placeRanking.ts` не трогаем — он исчезнет на интеграции;
оттуда переносятся идеи, а не код.

---

## 1. Шкала и формула

Итоговый скор места — число в `[0, 1]`:

```
score = clamp01( base(place) · weight(архетип, категория) · hourAffinity(hour)?
                 + bonusIndoor + bonusOpen + bonusWeather )
```

- Ядро — **мультипликативное**: качество × принадлежность архетипу. Вес 0
  означает «категория не участвует в архетипе вовсе», и никакое качество места
  этого не компенсирует. Так «лучший ТЦ города» не победит средний парк в
  зелёном вайбе.
- Контекстные бонусы **аддитивные** и маленькие (±0.04…0.15): они меняют порядок
  близких кандидатов, но не могут перепрыгнуть ядро.
- Все пороги и вклады — константы в коде, продублированы здесь с обоснованием.

## 2. Базовое качество места `base ∈ [0.50, 1.00] → clamp01`

Порт идеи `calculateQualityScore` из `placeRanking.ts` (шкала 0–100 → 0–1,
50 → 0.50) на контракт `GeoPlace`:

| Вклад | Число | Обоснование |
|---|---|---|
| База «ничего не знаем» | **+0.50** | Порт старого «базовый балл 50». Место без рейтинга и тегов — не ноль, а середина: OSM полон новых мест без рейтинга, и обнулять их значит навсегда хоронить окраины. |
| Рейтинг `place.rating` | **+ rating/5 · 0.30** | Самый сильный одиночный сигнал качества, но не решающий: у большинства OSM-мест рейтинга нет вообще, а там где есть — он часто от горстки оценок. Поэтому треть шкалы, не половина. |
| Прокси популярности по тегам | **+0…0.20** (кап) | У `GeoPlace` нет поля popularity — считаем по наличию OSM-тегов (см. таблицу ниже). |
| Размер парка | **+0…0.20** | Порт size-бонуса. Только `park`, только если источник дал площадь в `tags.area` (м²): `min(log10(area)·0.05, 0.20)`. Логарифм — потому что «в 10 раз больше» ощущается как «чуть лучше», а не «в 10 раз лучше». Нет площади → вклада нет: гадать размер по косвенным признакам не будем (принцип «никогда не врём про то, чего не знаем»). |

Прокси популярности (каждый тег — независимый признак «живого/заметного» места):

| Тег | Вклад | Обоснование |
|---|---|---|
| `wikipedia` / `wikidata` | **+0.08** | Статья о месте = заметность. Сильнейший из доступных сигналов, но не решающий: многие прекрасные «местные» места в Википедии не живут. |
| `website` | **+0.05** | Место с сайтом обычно поддерживает себя (актуальные часы, меню) — то есть «живое». |
| `opening_hours` | **+0.04** | Заполненные часы = обслуживаемое место; попутно это сырьё для будущего `hoursState`. |
| `phone` | **+0.03** | Слабый сигнал: немало хороших мест без телефона. Поэтому дешевле остальных. |

Кап 0.20 на всю группу: сигналы коррелируют (заметное место часто имеет и
статью, и сайт, и телефон) — без капа заметность считалась бы четырежды.
Старый `place.popularity` (0–20) этим заменяется.

**Не переносим:** хардкод `пушкин`/`кулибин` (+25). Городоспецифичный хак;
его роль («известный парк лучше») теперь честно делает тег `wikipedia`.

## 3. Архетипы

Каждый архетип — профиль `Archetype`:

```ts
interface Archetype {
  id: ArchetypeId;            // 'green' | 'coffee' | 'evening' | 'rainy' | 'surprise'
  labelRu; labelEn; descriptionRu; descriptionEn;
  categoryWeights: Record<CategoryId, number>;  // 9 категорий, 0..1
  indoorBias: number;         // 0..1 — желание крытого
  shadePriority: number;      // 0..1 — важность тени/зелени
  stayMinutes: Record<CategoryId, number>;      // сколько сидеть на остановке
  hourAffinity: (hour: number) => number;       // 0..1, кусочно-линейная
}
```

Инварианты (проверяются тестами): все 9 категорий присутствуют в
`categoryWeights` и `stayMinutes`; все числа конечные, веса и bias/priority в
`[0,1]`; `hourAffinity` на часах 0–23 выдаёт конечное значение из `[0,1]`;
id уникальны; тексты непустые на обоих языках.

### 3.1 green — «Зелёная»

Ядро: парки, скверы, набережные (PRODUCT.md). Тень и зелень важнее скорости.

| Категория | Вес | Почему |
|---|---|---|
| park | **1.0** | Ядро архетипа. |
| viewpoint | **0.7** | Набережные и панорамы — тоже «зелёная» улица, но без зелени в ядре. |
| attraction | **0.5** | Уличные достопримечательности украшают прогулку, не являясь её целью. |
| cafe | **0.4** | Веранда в парке — законная остановка передышки, но не ядро. |
| restaurant | **0.3** | Еда уводит из темпа прогулки; оставляем как вариант. |
| museum / bar | **0.2** | Почти несовместимо с «зеленью», но полностью нулевые веса ломают деградацию в плохую погоду. |
| cinema / shopping | **0.1** | Крытые ящики — противоположность архетипу; вес почти нулевой, но не ноль (диверсификация не должна остаться без вариантов). |

`indoorBias` **0.05** — архетип существует ради улицы. `shadePriority` **0.9** —
почти максимум: заявлено «тень важнее скорости».

### 3.2 coffee — «Кофейная»

Ядро: кафе, кондитерские, улочки; 1–2 сидячие остановки.

| Категория | Вес | Почему |
|---|---|---|
| cafe | **1.0** | Ядро. |
| restaurant | **0.7** | Сидячая остановка посерьёзнее; близко к ядру. |
| shopping | **0.5** | «Заглянуть по пути» — уличный шопинг естественно сшивает кофейные точки. |
| attraction / park | **0.4** | Фон между кофе, не цель. |
| bar | **0.3** | Вечерний сценарий, днём слабый. |
| museum | **0.2** | Заберёт полдня — ломает «1–2 сидячие остановки». |
| viewpoint | **0.3** | Милая точка на маршруте, не ядро. |
| cinema | **0.1** | Два часа тьмы против духа «прогуляться». |

`indoorBias` **0.6** — остановки крытые, но переходы между ними уличные.
`shadePriority` **0.3** — тень приятна, но кофейня и так крыша. `stayMinutes`:
cafe **30** (главная сидячая), restaurant 35, прочие 10–25.

### 3.3 evening — «Вечерняя»

Ядро: освещённые улицы, живые места; после 19:00, работает сейчас.

| Категория | Вес | Почему |
|---|---|---|
| bar | **1.0** | Ядро вечернего вайба. |
| restaurant | **0.8** | Ужин — вторая половина ядра. |
| attraction | **0.6** | Подсветка памятников/центра — бесплатный театр. |
| cinema | **0.6** | Вечерний сеанс — классика, но два часа внутри. |
| cafe | **0.5** | Спокойный вечерний вариант. |
| viewpoint | **0.5** | Ночные панорамы эффектны; небезопасность гасим в погодных модификаторах. |
| park | **0.2** | Парк ночью неосвещён и пуст — анти-ядро. |
| museum | **0.15** | Почти всё закрыто после 19:00 — вес отражает «работает сейчас». |
| shopping | **0.1** | Закрыто. |

`indoorBias` **0.5** — поровну улицы и заведений. `shadePriority` **0.1** —
ночью тень не нужна. `hourAffinity` — ключевой профиль архетипа (см. 3.6).

### 3.4 rainy — «Дождливая»

Ядро: музеи, галереи, ТЦ, крытые рынки; минимум улицы.

| Категория | Вес | Почему |
|---|---|---|
| museum | **1.0** | Ядро. |
| cinema | **0.9** | Второе ядро: два часа под крышей. |
| shopping | **0.9** | ТЦ и крытые рынки — прямо из ТЗ. |
| cafe | **0.8** | Сидеть у окна под дождём — отдельное удовольствие; крыто. |
| restaurant | **0.7** | Аналогично кафе, дольше. |
| bar | **0.5** | Крыто, но вечерний вайб; днём под дождём — нейтрально. |
| attraction | **0.3** | Часть аттракционов крытые, часть нет — компромисс. |
| park / viewpoint | **0.05** | Под дождём почти бессмысленны; не ноль ради деградации. |

`indoorBias` **0.95** — почти всё крыто. `shadePriority` **0.2** — дождь ≠
солнце, тень неактуальна. `stayMinutes`: museum 60, cinema 120, shopping 40,
cafe/restaurant/bar 30–35, park/viewpoint 5.

### 3.5 surprise — «Удиви меня»

Микс без явного ядра, максимум разнообразия якорей.

| Категория | Вес | Почему |
|---|---|---|
| viewpoint / attraction | **0.6** | Самые «неожиданные» точки города. |
| cafe / park | **0.55** | Рабочие лошадки любой прогулки, чуть ниже ядра. |
| museum / restaurant | **0.5** | Тяжёлые, но разнообразные. |
| bar / cinema / shopping | **0.45** | Спокойный низ без провалов. |

Разброс 0.45–0.6 — намеренный: полного равенства нет (профиль безвкусный),
явного ядра нет (это другой архетип). Разнообразие добивается бонусом
категории в диверсификации (§7). `indoorBias` **0.45**, `shadePriority` **0.5**
— нейтральные середины. `stayMinutes` — средние значения архетипов (10–120).

### 3.6 hourAffinity — кусочно-линейные профили

Функция задана опорными точками `[час → 0..1]`, между ними — линейная
интерполяция, вне диапазона — кламп, на стыке суток (24:00 = 0:00) — значение
точки 0. Часы целые 0–23 (проверяется тестами на всём диапазоне).

| Архетип | Точки (час → значение) | Чтение |
|---|---|---|
| green | 0→0.25, 6→0.35, 8→0.85, 11→1.0, 17→1.0, 19→0.8, 21→0.45, 24→0.25 | Парки живы с утра до заката; в 21 уже пусто и неосвещено. |
| coffee | 0→0.1, 6→0.25, 7→0.6, 8→0.85, 10→1.0, 16→1.0, 18→0.8, 20→0.5, 22→0.2, 24→0.1 | Утренний и дневной кофе — ядро; к 20–22 кофейни закрываются. |
| evening | 0→0.3, 6→0.05, 12→0.1, 16→0.4, 18→0.7, 19→0.9, 20→1.0, 23→0.9, 24→0.3 | До 16 архетип почти не существует; пик 19–23 (PRODUCT.md: «после 19:00»). |
| rainy | 0→0.35, 9→0.9, 10→1.0, 18→1.0, 19→0.75, 21→0.6, 23→0.4, 24→0.35 | Музеи — день, кино — вечер; после 23 остаётся мало крытого работающего. |
| surprise | 0→0.5, 7→0.6, 10→0.9, 12→1.0, 21→0.9, 23→0.7, 24→0.5 | Ровная с лёгким ночным спадом: удивить можно почти всегда. |

## 4. Эвристика indoor/outdoor по категории

`GeoPlace.indoor` отсутствует у большинства записей → дефолт по категории
(переопределяется явным полем места, если источник его дал):

| Категория | Дефолт indoor | Почему |
|---|---|---|
| museum, cinema, shopping | **true** | Сущностно крытые. |
| cafe, restaurant, bar | **true** | Зал крытой; терраса — надстройка, для скоринга крытого достаточно зала. |
| park, viewpoint | **false** | Сущностно уличные. |
| attraction | **false** | В OSM `tourism=attraction` чаще памятник/фонтан/уличный объект; галерея обычно помечена `tourism=museum`. |

## 5. Слагаемые `scorePlace(place, ctx) → {score, reasonsRu[], reasonsEn[]}`

### 5.1 fit = base · w · hourAffinity?

- `w = archetype.categoryWeights[place.category]` (неизвестная категория → 0.3:
  нейтральный «не ядро и не анти-ядро»; `PlaceCategory` контракта допускает
  произвольные строки).
- `hourAffinity(hour)` — множитель применяется только если контекст передал
  `hour` (инъекция времени; генератор передаёт, чистый скоринг — нет). Прямое
  умножение: архетип «не светится» вне своих часов.

### 5.2 bonusIndoor = 0.10 · (2·match − 1) ∈ [−0.10, +0.10]

`match = isPlaceIndoor ? indoorBias : 1 − indoorBias`. Симметрично: полное
соответствие +0.10, полное несоответствие −0.10, нейтральный bias 0.5 → 0.
Обоснование величины: ±0.10 способно поменять местами двух близких кандидатов,
но не может протащить крытый киоск мимо хорошего парка в ясную погоду (ядро
мультипликативно). preferIndoor отдельным слагаемым не начисляется — дождь уже
поднял `indoorBias` в `combineContext`, иначе дождь считался бы дважды.

### 5.3 bonusOpen (инъекция `ctx.hoursState?: 'open' | 'closed' | 'unknown'`)

| Значение | Вклад | Почему |
|---|---|---|
| open | **+0.10** | Большинство кандидатов открыто → «открыто» слабый подтверждающий сигнал, не преимущество. |
| closed | **−0.15** | Закрытое место — не якорь (гейт PRODUCT.md: «каждая остановка работает»), но жёсткую фильтрацию оставляем генератору; скоринг лишь сильно демотивирует. |
| unknown / отсутствие | **0** | Честное «не знаем» — не штрафуем. |

Поле структурное (`ScorePlaceContext` объявлен в зоне vibes), импортов из
чужих зон нет.

### 5.4 bonusWeather (из `weather` контекста через `mapToHints`)

| Условие | Вклад | Почему |
|---|---|---|
| preferShade && категория park | **+0.08** | Крона = тень; единственная категория, реально дающая укрытие от солнца. |
| preferShade && прочий outdoor | **−0.04** | Открытая остановка в жару неприятна, но не запрещена. |
| preferLighted && cafe/restaurant/bar | **+0.06** | Живые и освещённые места вечером — то, что хочет вечерний сценарий. |
| preferLighted && park/viewpoint | **−0.06** | Тёмно, пусто, небезопасно; зеркально к живым местам. |
| Погоды нет (null) | **0** | Деградация: скоринг = чистый архетип. |

## 6. Погода `src/lib/weather/index.ts` (Open-Meteo, без ключа)

`fetchWeatherContext(lat, lng, opts?) → Promise<WeatherContext | null>`:
`current=temperature_2m,precipitation,weather_code,is_day` + `hourly=` те же
поля на 24 ч, `timezone=auto`. Любая ошибка (сеть, не-2xx, кривой JSON,
пустые поля) → **null**, функция не бросает (PRODUCT.md: «честная деградация»).

```ts
interface WeatherContext { tempC: number; isRaining: boolean; precipNext2h: boolean; isDark: boolean }
```

| Поле | Порог | Обоснование |
|---|---|---|
| `isRaining` | current precipitation **≥ 0.1 мм/ч** | Ниже — морось/датчик-шум, по ней гуляют; с 0.1 уже мокро. |
| `precipNext2h` | max из двух ближайших часовых **≥ 0.2 мм** | Часовой прогноз сглажен; порог чуть выше, чтобы не пугаться несильного краткого дождя. |
| `isDark` | `is_day === 0` | Прямой ответ API, никаких локальных закатных таблиц. |

`mapToHints(ctx) → { preferIndoor, preferShade, preferLighted }`:

- `preferIndoor = isRaining || precipNext2h` — дождь идёт или вот-вот начнётся.
- `preferShade = !isRaining && !isDark && tempC > 27` — тень нужна только на
  солнце; ночью и под дождём она не нужна. Порог **27 °C** — конвенция ТЗ
  («жара >27 °C»): выше — некомфортно для ходьбы, тень важнее скорости.
- `preferLighted = isDark` — темно → нужны освещённые и живые места.

Кэш: в памяти процесса, ключ — координаты, округлённые до **0.1°**
(≈11 км; внутри ячейки погода различается меньше, чем точность прогноза).
TTL успеха — **30 мин** (погода меняется медленнее, берегём квоту API);
TTL отказа — **2 мин** (сетевой сбой не должен убивать погоду на полчаса,
но и долбить мёртвый API на каждый запрос нельзя). `fetchImpl` инъекцируется
для тестов; есть `resetWeatherCache()` для тестов.

## 7. Диверсификация — `selectDiverseAlternatives`

Порт жадного алгоритма из `placeRanking.ts`, но метрика — правильная:

**Эквидистантная (равнопромежуточная) проекция** якоря в локальную плоскость:

```
x = R · (λ − λ₀) · cos(φ₀)      y = R · (φ − φ₀)      R = 6 371 000 м
```

Сырые градусы в старом коде (в `distanceToRouteMeters`/`isInDirectionCone`)
врут по долготе на cos(широты): на широте Москвы cos 55.75° ≈ 0.56 —
расстояния по X почти вдвое меньше реальных. Проекция даёт ошибку <0.5% на
масштабе прогулки (≤10 км) и O(1) на пару точек вместо тригонометрии.

Жадный отбор (все кандидаты уже имеют `score`):

```
itemValue = score
          + diversityBonus      = min(minDistToSelected / diversityRadius, 1) · 0.30
          − proximityPenalty    = max(0, (dAnchor − dPrimary)/200) · 0.12
          − categoryRepeat      = 0.08 · (сколько уже выбрано той же категории)
```

- 0.30 / 0.12 — порт старых 30/12 баллов на новую шкалу.
- `categoryRepeat` — новое: разные якоря лучше кучи одинаковых кафе; для
  «удиви меня» это половина смысла архетипа.
- `diversityRadius` по умолчанию **300 м** (как в старом): два якоря ближе 300 м
  друг от друга почти не добавляют прогулке разнообразия.
- Кандидаты дальше `max(1.5 · dPrimary, 1200)` от якоря не рассматриваются
  (порт старого поведения).

## 8. Связка — `combineContext(archetype, weather | null, now) → AdjustedProfile`

Возвращает **новый** объект (вход не мутируется) — копию архетипа со
скорректированными весами и bias/priority плюс список сработавших правил
`adjustments` (для причин и тестов). Правила аддитивны и капятся, стекать
могут (тропический ливень при +28 °C — реальность):

| Правило | Условие | Эффект | Обоснование |
|---|---|---|---|
| rain-indoor | `weather && (isRaining \|\| precipNext2h)` | `indoorBias += 0.25` (кап 1); крытым категориям (museum, cinema, shopping) вес **+0.15** (кап 1); уличным (park, viewpoint) вес **−0.20** (пол 0) | Дождь — сильнейший модификатор: он меняет саму возможность остановки, а не комфорт. ±0.25 bias'а при капе [0,1] не превращает зелёный вайб в дождливый (0.05→0.30), но парку под ливнем честно режет вес. |
| heat-shade | `weather && tempC > 27` | `shadePriority += 0.30` (кап 1); park вес **+0.15** | Жара неприятна, но улицу не отменяет — слабее дождя. Зелень = тень + прохлада. |
| dark-evening | `weather ? weather.isDark : (hour < 7 \|\| hour ≥ 19)` | Веса: `w → w + (evening.w − w) · 0.25` | Тьма подмешивает 25% вечернего профиля: bar у green 0.2→0.40, park 1.0→0.80. Контекст подправляет выбор, но не переписывает его — юзер выбрал зелёный, а не вечерний. Fallback по часу, когда погоды нет: грубо (зимой темнеет в 17), но честно и без зависимостей. |

Погодных данных нет (`weather = null`) → `rain-indoor`/`heat-shade` не
срабатывают вовсе, срабатывает только часовой fallback `dark-evening`.

## 9. Деградация (сводка)

| Не знаем | Поведение |
|---|---|
| Погода (null / сеть упала) | hints нейтральные, weather-бонусы = 0, combine = чистый архетип + часовой fallback |
| Часы работы | `hoursState` отсутствует/unknown → вклад 0 |
| Площадь парка | size-вклад = 0 |
| `indoor` у места | Дефолт по категории (§4) |

## 10. Открытые вопросы

1. `tags.area` в OSM почти не встречается — считать площадь полигона придётся
   в geo-адаптере (вне зоны этой ветки). Пока size-бонус работает только там,
   где адаптер отдал площадь.
2. Порог жары 27 °C и капы (0.25/0.30/0.15) — конвенции первого прогона;
   вынести в настройку при появлении сезонности/климатических зон.
3. Кто считает `hoursState` (парсер `opening_hours`) — следующий шаг, в эту
   зону не входит; интерфейс инъекции уже готов.
4. `hourAffinity` принимает целый час; если генератору понадобится получасовая
   гранулярность — интерполяция уже её поддерживает (аргумент дробный).
