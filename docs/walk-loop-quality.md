# Волна «Прогулка, а не кратчайший путь» — дизайн-док

> Статус: чернова́к к реализации. Контракт: docs/PRODUCT.md (формула прогулки,
> метрика из 5 гейтов). Эта волна не добавляет новых данных — она разворачивает
> целевую функцию существующего движка. Уличный интерес-слой — следующая волна
> (см. §9 roadmap этой волны).

## Диагноз (из разведки кода, 2026-11-17)

Бюджет в движке — **только потолок**: жадный набор останавливается при
`1.1·B` (`createWalkPlan.ts:375-393`), механизма добора до пола `0.9·B` нет;
`walk_share` и недобор ловятся гейтами, но гейты только помечают
(`gates.ts:34-63`). Воронка кандидатов проксимити-формы на каждом этаже:
радиус `0.4·B` (`quickPipeline.ts:37-40`) → Overpass «12 ближайших на
категорию» (`overpass-places.ts:220-223`) → скор со штрафом `−proximity/zone`
(`selection.ts:57-62`) → жадный набор в этом порядке. Порядок обхода —
NN+2-opt на минимум времени (`ordering.ts:29-97`); при равных скорах
сортировка вариантов предпочитает *короткий* план (`createWalkPlan.ts:183-188`).
Ноги — кратчайшая уличная сшивка (`route([a,b])`, `createWalkPlan.ts:433-441`);
поле `alternatives` в `RouteRequest` (`geo/types.ts:42`) ORS-адаптером не
реализовано и движком не используется.

Итого: движок честно строит **короткий замкнутый тур по ближайшим местам**.
Продукт обещает **прогулку**, уложенную в бюджет, — не минимальную.

## Целевое поведение

Бюджет — **коридор** 0.9–1.1·B. План короче 0.9·B — недобор, который движок
пытается закрыть (добавление остановок, удлинение ног через альтернативы),
а не просто помечает. Кандидаты набираются по ценности с географической
диверсификацией, а не «ближайшие N». Длинные ноги ходят не одним кратчайшим
маршрутом, если есть непересекающаяся альтернатива. Гейты после ремонта
честно видны в UI.

## R1. Коридор бюджета: `fillToFloor`

После финальных ног плана (когда метрики реальные), если
`totalMinutes < MIN_BUDGET_SHARE·B` (новая константа `0.9` в `types.ts`,
рядом с `BUDGET_TOLERANCE`):

1. **Добрать остановкой.** Следующий по скору кандидат из пула, чья нога
   влезает в потолок `1.1·B` (матрица уже посчитана). Повторять, пока пул не
   кончится или потолок не упрётся. Соблюдать `categoryLimits` и `MAX_STOPS`.
2. **Добрать ногой.** Если кандидатов больше нет: взять длиннейшую ногу и
   построить через неё путь с via-точкой — `route([a, via, b])`, где via —
   точка на перпендикуляре к середине ноги, отстоящая на недостающие
   метры (линейная оценка через текущую скорость маршрута). Целевое
   удлинение: недостающие минуты ±10%. Ограничение: ≤2 таких ног на план,
   гейт `loop_no_repeat_street` обязан пройти (via может замкнуть «туда-обратно»
   — проверка гейтом отсекает).
3. **Честный отказ.** Если и это не дотянуло — план возвращается как есть;
   gateReport показывает недобор в `detail`. Наливать фиктивные минуты
   запрещено (принцип «честная деградация»).
4. Вторая волна поиска (`SECOND_WAVE_MULTIPLIER = 1.75` в `quickPipeline.ts`)
   при недоборе первой сборки запускается принудительно, если ещё не
   запускалась, — раньше она включалась только по эскалации «мало кандидатов».

`fillToFloor` живёт в `createWalkPlan.ts` как шаг финальной сборки варианта,
вызывается для каждого варианта до сортировки. Кэш порта делает повторные
route-вызовы дёшевыми (диск 30 дней).

## R2. Воронка без проксимити-перекоса

- Overpass: `limit` per-category 12 → 20 (`categories.ts` радиусы остаются;
  это не квота роутера, ответ длиннее на треть — приемлемо). В движок по-прежнему
  уходит шорт-лист `ENGINE_CANDIDATE_CAP = 24`.
- Скор отбора (`selection.ts:57-62`): член `−proximity/zone` теряет
  доминирование — вес ×0.25 (качество места + архетип выбирают КУДА, близость —
  мягкий тайбрейкер). Константа `PROXIMITY_WEIGHT = 0.25` с комментарием-мотивом.
- Азимутная диверсификация в `quickPipeline.scoreCandidatePool`: до нарезки
  шорт-листа кандидаты группируются по 8 секторам вокруг старта
  (azimuth = atan2 по гаверсинус-проекции), потолок на сектор
  `SECTOR_CAP = 6`. Гарантирует, что в шорт-лист попадают кандидаты из разных
  частей зоны — жадный набор получает материал для кольца, а не клубка.
- Сортировка вариантов при равных скорах (`createWalkPlan.ts:183-188`):
  вместо `totalMinutes` ASC — предпочесть вариант с большим числом прошедших
  гейтов, затем большим `loopCoverage` (площадь выпуклой оболочки полилинии
  петли, `shoelace` по проекции), затем меньшим totalMinutes. Площадь —
  дешёвый прокси «накрыли район, а не клубок».

## R3. Ноги с альтернативами

- `ors.ts`: реализовать `RouteRequest.alternatives` → ORS body
  `alternative_routes: { target_count, share_factor: 0.6 }` (docs ORS v2
  directions; ответ — FeatureCollection с несколькими features). Адаптер
  возвращает их через НОВЫЙ опциональный метод порта: в `ports.ts` добавить
  `routeAlternatives?(req: RouteRequest): Promise<RouteSegment[]>` —
  основной маршрут первым. Обратная совместимость: строгий движок использует
  метод, если есть; фейк-порты тестов реализуют детерминированно.
- Движок (`createWalkPlan.ts`, сборка ног): для ног > `LEG_ALT_MIN_MINUTES = 8`
  (константа в `types.ts`) — запрос альтернатив (≤3 total). Выбор:
  (а) минимум пересечения с уже принятыми ногами — переиспользовать
  `fractionWithinCorridor` (`internal/geo.ts:106-126`) попарно;
  (б) при равном пересечении — самый длинный, который влезает в потолок
  `1.1·B`; (в) без альтернатив — основной.
- Квота: альтернативы только в финальной сборке ног (не в матрице), ≤3
  route-вызовов на ногу; дисковый кэш 30 дней делает повторные прогулки
  бесплатными. Лег-метрики в `gateReport` помечаются `routeVariant: 'alt'`.

## R4. Гейты-ремонт

`walk_share` чинится сам: добор остановок/ног в R1 увеличивает ходьбу.
Отдельного ремонтного цикла нет — R1 и есть ремонт. Всё, что не дотянуто,
возвращается с честно упавшими гейтами (как сегодня).

## R5. Честность в UI

`uiAdapter.ts`: `UiWalkPlan` получает `gatesSummary: { name: WalkGateName;
pass: boolean; detail?: string }[]` (плокий массив, без ссылок на движковые
объекты — `replaceStop.ts:30-35` перестаёт терять их). `WalkSummaryCard`:
при провале любого гейта — одна строка-заметка человеческим языком
(«прогулка вышла короче плана: рядом мало мест», «много сидения, мало ходьбы»)
+ существующий amber-механизм. Новых i18n-ключей ≤4.

## R6. Техдолг по пути (без перестройки)

- `internal/geo-utils.ts`: `isFiniteLatLng / validateInput / errMessage` —
  один модуль вместо трёх копий (`createWalkPlan.ts:580-629`,
  `loopThrough.ts:272-302`, `streetLoop.ts:277-303`).
- `quickPipeline.ts:38`: литерал скорости → `DEFAULT_WALKING_SPEED_KMH`.
- Зона: одна функция `zoneMetersForBudget(budgetMin, speedKmh)` в
  `internal/geo.ts`; call-sites `quickPipeline.ts:37-40` и
  `createWalkPlan.ts:262-279` переходят на неё (формула остаётся прежней —
  консолидация, не смена чисел).

## Тесты (vitest, фейковый grid-city порт)

- `fillToFloor`: пул позволяет 55-мин план при бюджете 60 → итог в [54, 66];
  пул исчерпан → честный недобор с gateReport, без фиктивных минут.
- `fillToFloor` шаг «ногой»: via удлиняет длиннейшую ногу, гейт
  `loop_no_repeat_street` отсекает via-туда-обратно.
- альтернативы: фейк-порт отдаёт 2 маршрута (пересекающийся короче / непересекающийся
  длиннее влезает в потолок) → выбран непересекающийся.
- азимуты: пул, где 20 лучших кандидатов в одном секторе и 8 в других →
  шорт-лист содержит ≥2 сектора.
- `loopCoverage`: варианты с равным скором — побеждает большее покрытие.
- регресс: все существующие тесты зелёные (сейчас 499).

## Не делаем в этой волне

Уличный интерес-слой и `out geom` (следующая волна), микростопы, эксперт-режим,
UI-перестройка кроме R5, maplibre.

## Роадмап следующих волн (для контекста, не эта волна)

Волна «улицы» — Overpass `out geom` для линейных фич (парки-полигоны, вода,
пешеходные улицы), StreetInterest-скор секторов, снап вейпоинтов розы
`streetLoop` к интересным точкам, микро-стопы «по пути».
Волна «human design» — maplibre-рендер, вход с главного экрана, шторка 45/85,
шаринг быстрой прогулки, человеческие причины.
